# Cisco BGP Troubleshooting Lab – R1

## 📌 Lab Overview

This lab focuses on troubleshooting a network where **R1 has three intentional misconfigurations** affecting OSPF and BGP operation.

R1 is expected to:

- Establish an **eBGP peering** with SPR1.
- Advertise the loopback interfaces of **R1, R2, and R3**.
- Advertise a `10.0.0.0/16` summary to SPR1 through eBGP.
- Provide connectivity from R2/R3 to the external server `15.0.0.1`.

The objective is to identify and correct the three misconfigurations on R1 and verify connectivity from the internal network to the external server.

---

# 🎯 Lab Objectives

The lab requires the following:

1. Troubleshoot the three misconfigurations on R1.
2. Restore OSPF adjacency between R1 and the internal routers.
3. Ensure the eBGP relationship between R1 and SPR1 operates correctly.
4. Ensure R1 advertises the required loopback addresses through BGP.
5. Ensure R1 advertises the `10.0.0.0/16` summary through BGP.
6. Test connectivity from R2 or R3 to `15.0.0.1`.

---

# 🧪 Initial Problem

The first indication of a problem was generated by OSPF:

```text
%OSPF-4-ERRRCV: Received invalid packet: mismatch area ID,
from backbone area must be virtual-link but not found from
10.0.13.1, GigabitEthernet0/2
```

A similar message was received from the R2 connection:

```text
%OSPF-4-ERRRCV: Received invalid packet: mismatch area ID,
from backbone area must be virtual-link but not found from
10.0.12.1, GigabitEthernet0/1
```

These messages indicate an **OSPF area mismatch** between R1 and its neighbors.

---

# 🔎 Misconfiguration 1 – Incorrect OSPF Area

## Problem

R1 had the following OSPF configuration:

```text
router ospf 1
 network 0.0.0.0 255.255.255.255 area 1
```

The internal interfaces were therefore being placed into **OSPF area 1**, while the neighboring routers expected them to participate in **area 0**.

This caused OSPF adjacency problems.

---

## Fix

The incorrect area statement was removed:

```text
R1(config-router)#no network 0.0.0.0 255.255.255.255 area 1
```

It was then replaced with the correct area:

```text
R1(config-router)#network 0.0.0.0 255.255.255.255 area 0
```

The corrected OSPF configuration is:

```text
router ospf 1
 log-adjacency-changes
 passive-interface GigabitEthernet0/0
 network 0.0.0.0 255.255.255.255 area 0
 default-information originate
```

After correcting the area, the OSPF adjacency with R2 came up:

```text
%OSPF-5-ADJCHG: Process 1, Nbr 2.2.2.2
on GigabitEthernet0/1 from LOADING to FULL, Loading Done
```

This confirms that the OSPF area mismatch was resolved.

---

# 🔎 Misconfiguration 2 – Incorrect BGP Summary Advertisement

## Problem

The original BGP configuration contained:

```text
network 10.0.0.0
```

This does **not** explicitly specify the required `/16` mask.

The lab requires R1 to advertise:

```text
10.0.0.0/16
```

to SPR1.

---

## Fix

The incorrect statement was removed:

```text
R1(config-router)#no network 10.0.0.0
```

The correct statement was then configured:

```text
R1(config-router)#network 10.0.0.0 mask 255.255.0.0
```

The resulting BGP table showed:

```text
*> 10.0.0.0/16       0.0.0.0
```

This confirms that R1 was originating the required `/16` summary into BGP.



---

# 🔎 Misconfiguration 3 – Missing/Incorrect Route Supporting the BGP Summary

## Problem

For R1 to originate:

```text
10.0.0.0/16
```

using the BGP `network` command, the corresponding prefix needs to exist in R1's routing table.

The required summary route is:

```text
10.0.0.0/16
```

R1 therefore needs a route that exactly matches the BGP network statement.

---

## Fix

A static route to the Null0 interface was configured:

```text
R1(config)#ip route 10.0.0.0 255.255.0.0 Null0
```

The resulting routing table confirmed:

```text
S       10.0.0.0/16 is directly connected, Null0
```

This provides R1 with the exact `/16` route required for BGP origination.

---

# 🧠 Why Null0 Is Important

The lab uses a summary route:

```text
10.0.0.0/16
```

to represent the internal `10.0.x.x` networks.

The more-specific internal routes are still used when available, such as:

```text
10.0.12.0/30
10.0.13.0/30
```

The Null0 route acts as a discard route for traffic matching the `/16` summary that does not match a more-specific route.

More-specific routes have priority because of **longest-prefix matching**.

# 🔎 Verifying the BGP Configuration

After fixing the configuration, `show ip bgp` displayed:

```text
BGP table version is 11, local router ID is 1.1.1.1

   Network          Next Hop            Metric LocPrf Weight Path
*> 1.1.1.1/32        0.0.0.0                  0     0 32768 i
*                    100.0.0.1                0     0     0 65001 i
*> 10.0.0.0/16       0.0.0.0                  0     0     0 65000 i
*                    100.0.0.1                0     0     0 65001 i
*> 15.0.0.0/8        100.0.0.1                0     0     0 65001 65002 i
```

The important entry is:

```text
*> 10.0.0.0/16       0.0.0.0
```

The `*>` indicates that the route is **valid and selected as the best route**.

The BGP table also shows that R1 successfully learned the external network:

```text
*> 15.0.0.0/8  100.0.0.1  ... 65001 65002 i
```

This confirms that R1 has a valid BGP path toward the external network.

# 🔧 Final R1 Configuration

After troubleshooting, the relevant R1 configuration was:

```text
interface Loopback0
 ip address 1.1.1.1 255.255.255.255

interface GigabitEthernet0/0
 ip address 100.0.0.2 255.255.255.252

interface GigabitEthernet0/1
 ip address 10.0.12.1 255.255.255.252

interface GigabitEthernet0/2
 ip address 10.0.13.1 255.255.255.252

router ospf 1
 log-adjacency-changes
 passive-interface GigabitEthernet0/0
 network 0.0.0.0 255.255.255.255 area 0
 default-information originate

router bgp 65000
 bgp log-neighbor-changes
 no synchronization
 neighbor 100.0.0.1 remote-as 65001
 network 1.1.1.1 mask 255.255.255.255
 network 2.2.2.2 mask 255.255.255.255
 network 3.3.3.3 mask 255.255.255.255
 network 10.0.0.0 mask 255.255.0.0

ip route 0.0.0.0 0.0.0.0 100.0.0.1
ip route 10.0.0.0 255.255.0.0 Null0
```

The final running configuration confirms the corrected OSPF area and correctly masked BGP summary statement.

# 🧭 Troubleshooting Approach

A useful troubleshooting sequence for this type of lab is:

```text
1. Test connectivity
       ↓
2. Check routing table
       ↓
3. Check OSPF neighbors
       ↓
4. Check OSPF areas
       ↓
5. Check BGP neighbor status
       ↓
6. Check BGP table
       ↓
7. Check BGP network statements
       ↓
8. Check whether advertised routes exist in RIB
       ↓
9. Check the Null0 summary route
       ↓
10. Test connectivity again
```

This approach helps isolate whether the problem is with the **IGP, BGP peering, BGP route origination, or forwarding**.

# 🏁 Key Takeaways

### 1. OSPF Area Consistency Matters

Routers forming an OSPF adjacency must agree on the area associated with the link. An area mismatch prevents normal adjacency formation.

### 2. BGP `network` Statements Are Exact

The BGP network statement:

```text
network 10.0.0.0
```

is different from explicitly advertising:

```text
network 10.0.0.0 mask 255.255.0.0
```

When a specific prefix length is required, explicitly specify the mask.

### 3. The Route Must Exist in the Routing Table

For R1 to originate:

```text
10.0.0.0/16
```

the corresponding route must exist in its routing table.

The Null0 route provides that exact route:

```text
ip route 10.0.0.0 255.255.0.0 Null0
```

### 4. Verify Both Control Plane and Data Plane

Seeing a route in the BGP table is not enough. Always verify:

```text
show ip bgp
show ip route
show ip bgp summary
ping 15.0.0.1
```

The ultimate test is whether traffic can actually reach the external server.
